## Access and scope

The admin API exposes every operation in the moderator UI except impersonation.
The UI and API use the same services; existing moderator routes retain their JWT behavior.
Use the API origin (`https://api.opnform.com`) and `/external/admin/v1` paths. There is no additional `/api` prefix on this origin.

Every request requires a real Sanctum personal access bearer token, the `admin-api:v1` marker,
an explicit operation scope, and an owner who is still an unblocked moderator. Wildcard and ordinary customer tokens do not grant admin access.
There is no public token-minting endpoint for admin scopes. A trusted server operator issues tokens:

```bash
php artisan admin-api:token support@example.com --name=Bureau --days=30 \
  --ability=admin:users:read --ability=admin:users:block --ability=admin:users:unblock
php artisan admin-api:token support@example.com --revoke=123
```

The first command prints the secret once. Store it in Bureau's bearer-token vault field.
Expiration is required (1–90 days); losing moderator status, blocking the owner, expiration,
or deletion revokes access. The worker checks authorization again before execution.
Customers cannot add admin abilities through Settings → API tokens.

## Read endpoints

| GET path under `/external/admin/v1` | Scope | Response |
| --- | --- | --- |
| `/users/{identifier}` | `admin:users:read` | User ID, email, name, blocked state, 2FA state, workspace summaries; identifier accepts ID, email, or form slug |
| `/workspaces/{id}` | `admin:workspaces:read` | ID, name, plan, form count |
| `/users/{user}/billing/customer` | `admin:billing:read` | Billing name and email |
| `/users/{user}/billing/subscriptions` | `admin:billing:read` | Latest 100 subscriptions |
| `/users/{user}/billing/payments` | `admin:billing:read` | Latest 24 paid invoices and refund status |
| `/users/{user}/deleted-forms` | `admin:forms:read` | Deleted forms, IDs, slugs and deletion dates |
| `/actions/{action_id}?operation=...&user_id=...` | The action's own scope | State, precondition hash, execution status and bounded result |

Admin accounts cannot be targeted by this API. Responses omit credentials, unrestricted user metadata and impersonation tokens.

## Actions

POST to `/external/admin/v1/actions/{operation}`. All requests require an `Idempotency-Key`
header (8–200 ASCII letters, digits, `.`, `_`, `:`, `-`), a client-generated UUID `action_id`,
and the `expected_state` hash returned by the action read endpoint.
Unknown JSON fields are rejected.

| Operation | Scope | Additional body fields |
| --- | --- | --- |
| `block-user` | `admin:users:block` | `user_id`, `reason` |
| `unblock-user` | `admin:users:unblock` | `user_id`, `reason` |
| `send-password-reset-email` | `admin:users:password-reset` | `user_id` |
| `disable-two-factor-authentication` | `admin:users:disable-2fa` | `user_id`, `reason` |
| `clear-user-cache` | `admin:users:clear-cache` | `user_id` |
| `apply-discount` | `admin:billing:discount` | `user_id` |
| `extend-trial` | `admin:billing:extend-trial` | `user_id`, `trial_ends_at` |
| `cancel-subscription` | `admin:billing:cancel` | `user_id`, `subscription_id`, `cancellation_reason` |
| `refund-payment` | `admin:billing:refund` | `user_id`, `invoice_id`, `refund_reason`, `expected_amount`, `expected_currency` |
| `update-customer` | `admin:billing:update` | `user_id`, `billing_email`, `billing_name` |
| `restore-form` | `admin:forms:restore` | `slug` |
| `create-template` | `admin:templates:create` | `template_prompt` |

Block/unblock snapshots expose a streaming form-state hash and counts rather than all form metadata; verification checks form effects as well as the user flag.

Reasons are required strings up to 1,000 characters. `trial_ends_at` is an absolute timestamp
after now and at most 14 days away. `template_prompt` is at most 4,000 characters; template generation publishes a listed template, just like the UI.
Cancellation applies at the subscription period end using the existing Cashier behavior.
Refunds are limited to the user's latest invoice. Supply the exact remaining amount in minor currency units as `expected_amount` and its lowercase currency as `expected_currency`; these appear in the approval body and are checked again before refunding. Split/shared payments require manual review and are refused. The installed Stripe Basil contract uses invoice payments and plural subscription discounts.
Discounts use the configured student/NGO coupon.

## Prepare, execute and verify

1. Generate a UUID and read `/actions/{uuid}?operation=block-user&user_id=42`.
2. Review the returned target and state. Copy `snapshot_hash` into `expected_state`.
3. Obtain the business approval in the calling integration.
4. POST the exact parameters with a unique `Idempotency-Key`.
5. Poll the same GET endpoint. Do not infer completion from HTTP 202.

```json
{
  "action_id": "8124f626-f5d0-4ca8-8c26-d58b38421644",
  "operation": "block-user",
  "status": "not_started",
  "target": "user:42",
  "snapshot_hash": "<64-character SHA-256 hash>",
  "state": {"id": 42, "blocked": false},
  "result": null
}
```

A request queues durable work and returns `202` with `action_id` and `status`.
The status progresses through `queued`, `running`, `verifying`, and `completed`. A receipt is persisted before read-back. `verifying` retains the target reservation; subsequent GET requests reconcile the receipt without repeating the write and release the reservation only after confirmation.
`rejected` means authorization, state or target locking prevented execution.
`uncertain` means an external effect may have occurred; the write is never retried automatically.
`verification_pending` means the command completed but a fresh read does not confirm the expected state.
A password reset's `completed` status means the mailer accepted it, **not** that the email was delivered.
Cache clearing similarly acknowledges the command; later cache repopulation is normal.
Refund completion requires Stripe's refund status to be `succeeded`, with the recorded charge ID and approved amount/currency. Reconciliation reads this receipt independently of newer invoices.

For `restore-form`, supply `slug` instead of `user_id` in the read query.
For `create-template`, supply only `operation=create-template`; the client UUID identifies the new resource before it exists.

Same key and canonical payload returns the existing action without execution. Different content,
another key for the same action UUID, or reuse across tokens returns `409`.
Hashes ignore JSON object key ordering. Token deletion does not erase the audit record.

## Bureau configuration

Import the [complete 30-operation YAML configuration](./bureau.yaml), set its test user ID,
and grant the corresponding token scopes. Select operations and grant the Support module's optional HTTP capability.
The YAML contains six resource reads and twelve action/read-verifier pairs.
Every action has a confirmation and a read-back verifier. The agent must first read the action status,
then copy its `snapshot_hash` into the action's `expected_state` parameter. YAML does not automatically copy response fields into subsequent requests.

The API does not depend on Bureau or Crisp. Bureau owns durable user approval; the product API owns
credentials, authorization, preconditions, execution and audit.

## Deployment and recovery

Apply migrations, configure a real asynchronous queue, and run the normal queue worker.
`sync` and `null` queue drivers are refused with `503` before recording a new action.
Jobs have one attempt and a 120-second timeout. The database/Redis retry-after default is 180 seconds (`QUEUE_RETRY_AFTER`). Keep queue visibility/retry-after **above 120 seconds**, including SQS configuration.
The database stores encrypted request payloads; queue messages carry only an action UUID.
Keep the application encryption key stable. Do not purge action records while their idempotency keys can be reused.

The API rate limit is 60 requests per minute per owner/IP. Stripe reads have a 2-second connect timeout
and 4-second request timeout, with a 9-second cumulative request budget and SDK retries disabled; remote unavailability can prevent preparation or verification.
A precondition is rechecked just before execution. It cannot provide an atomic lock against
independent Stripe dashboard edits or existing UI requests.

An uncertain or verifying action retains its target lock so another API action cannot hide or repeat a partial result.
If a process dies before queue publication, the row may remain queued; if it dies after its claim it may remain running.
Do not resend with a new UUID. An operator must inspect the action audit, queue and remote state,
record the actual outcome, and release its `admin_api_action_locks` row only after reconciliation.
Never reset an uncertain/running row to queued. The API intentionally provides no token-accessible override.

HTTP errors: `401` missing/expired token; `403` insufficient scope/role or protected target;
`404` unknown resource/operation; `409` changed state or key conflict; `422` invalid input;
`429` rate limit; `503` unsupported queue configuration. Remote failures may return `5xx` and must not trigger blind write retries.
